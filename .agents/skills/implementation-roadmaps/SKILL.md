# Implementation roadmap design

## Goal

Make a roadmap that communicates outcomes, sequence, dependencies, and evidence without implying false certainty.

## Workflow

1. Define the audience, planning horizon, product outcome, scope, and constraints.
2. Group work by user or system outcome rather than by a flat list of technical activities.
3. Sequence milestones using dependencies, risk reduction, learning value, and team capacity.
4. For each milestone, state the outcome, deliverables, acceptance evidence, dependencies, and explicit exclusions.
5. Add decision points and review dates for uncertain work; identify what would change the order or scope.

## Decision rules

- Separate committed work from exploratory opportunities and unprioritized ideas.
- Use relative order or ranges when dates are uncertain; do not invent precision.
- Prefer an early milestone that tests the riskiest assumption or integration.

## Boundaries

- Do not represent estimates as commitments unless the owner confirms them.
- Do not use a roadmap as a substitute for implementation-level acceptance criteria.

## Completion standard

Return the requested artifact or findings with enough evidence for a reviewer to understand what changed, what was checked, and what remains uncertain. Distinguish observed facts, inferred risks, and unverified assumptions. Keep the scope tied to the user's request.
